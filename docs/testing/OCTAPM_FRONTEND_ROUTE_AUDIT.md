# OctaPM frontend route audit

Every row was produced by navigating a real Chromium browser to the route as a
signed-in PM, waiting for the app shell, then reading the rendered body and the
console. Generated by `frontend/e2e/01-auth-and-navigation.spec.ts`.

"Page loads" means the body rendered real content, not a blank screen.
"Errors" counts console errors attributable to that navigation. "Project
context" means the project name was still in the header, proving the module did
not lose which project it belongs to.

`procurement` appears nowhere in `project-modules.ts` or `project-detail.tsx`.
A Procurement user signs in and has no procurement screen. Long-lead items —
which are part of the same permission module — *do* have an interface, reached
through the schedule.

## Caveats

- Rendering is not function. A module that renders is proven mounted, in
  context, and free of load errors. Whether its buttons complete a business
  workflow is a separate question, answered per-workflow in
  `OCTAPM_BROWSER_E2E_REPORT.md` and `OCTAPM_INTEGRATION_MAP.md`.
- Swept as PM only. A role with narrower permissions may see different pages.
- Project sub-tabs (for example Cost › Budget, Commercial › Change Orders) were
  exercised in the workflow suites, not swept exhaustively here.
